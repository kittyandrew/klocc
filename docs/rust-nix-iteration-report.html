Takeaway

The fastest path is not replacing Rust or replacing Nix. The fastest path is assigning them different jobs. Cargo is the inner-loop compiler. Nix is the reproducibility boundary, binary-cache protocol, and proof runner.

P0 / Inner Loop

Run `cargo check -p ...` and targeted `cargo test -p ...` inside `nix develop`. This keeps the correct native dependencies while preserving Cargo incremental state.

P0 / Keep Crane

The repo already uses `crane` correctly: package-specific `buildDepsOnly`, clean Cargo sources, and separate package derivations.

P1 / Outer Proofs

Use Nix package builds and VM snapshots after the fast loop passes. They are reproducible proofs, not keystroke-latency tools.

cargo = fast feedback crane = dependency cache layer VM snapshots = acceptance proof

Current Repo Shape

The build is already structured around `crane` and `fenix`. The slow part is mostly where the workflow lands: release-grade Nix derivations and compositor VM tests are being used during exploratory iteration.

FileObservation

Measured locally: `klocc-gui` runtime output was about 29.3 MiB with a 143.9 MiB runtime closure. Current package/check outputs were already locally available after recent builds, which is exactly how Nix cache reuse should look.

How Nix Cache Works

Nix cache hits are exact-store-path hits. Cargo incremental hits are mutable `target/` hits. Those are different animals, and confusing them is where iteration loops get painful.

+------------------+  source edit  +--------------------+  new drv  +-------------------+
| working tree     | -----------> | cleanCargoSource   | --------> | package build     |
+------------------+              +--------------------+           +-------------------+
        |                                   |                                 |
        | cargo inner loop               | dependency artifacts            | binary substituter
        v                                   v                                 v
   target/ cache                    crane buildDepsOnly              exact /nix/store path

Local `/nix/store`Exact store pathsRe-running the same derivationNew paths after source/flag/env changes
Binary substituterRemote exact store pathsSharing builds across machinesDirty local derivations never uploaded
Flake eval cacheEvaluation for a flake versionRepeated eval of same outputBuild time or changed derivations
Fixed-output derivationsContent-addressed fetch/vendor outputsCrate/source fetching reuseCompiled Rust reuse
`crane.buildDepsOnly`Dependency-only Cargo artifactsAvoiding dependency recompilesAvoiding local crate recompiles
Cargo `target/`Incremental compiler artifactsFast source edit rebuildsNix package reproducibility
`sccache`rustc invocationsRepeated local/CI compilesBinary/link steps and path churn

Rust-on-Nix Tool Comparison

For this workspace, `crane` remains the best default. Per-crate systems can improve binary-cache granularity, but they add generated files, evaluation surface, and native-crate override work.

ToolCache GranularityBest UseTradeoff
`crane`Dependency artifact derivation plus package/check derivationsCargo-native workspaces with good Nix checksCoarser than per-crate systems, much simpler
`buildRustPackage`Vendor/fetch deps plus one package derivationPackaging one Rust app in nixpkgs styleLess ergonomic for check matrices and artifact reuse
`naersk`Dependency derivation plus main derivationSimple Rust projectsLess explicit/check-composable than `crane`
`cargo2nix`One derivation/function per crateCI/cache-heavy projects accepting generated NixMore eval, generated `Cargo.nix`, git dependency caveats
`crate2nix`One derivation per crate via `buildRustCrate`Per-crate Nix incrementalityGenerated file or IFD plus crate override burden
`sccache`Compiler invocation cacheCargo inner loop or CI with remote cacheNot a replacement for Nix binary caches

Recommended Workflow

CLI / scanner edit loop

nix develop -c cargo check -p klocc
nix develop -c cargo test -p klocc

GUI edit loop

nix develop -c cargo check -p klocc-gui
nix develop -c cargo build -p klocc-gui

Live GUI with Cargo binary

KLOCC_GUI_BIN=target/debug/klocc-gui \
  nix develop -c klocc-gui-wayland-live start artifact.sqlite

Reproducible proof

nix build .#packages.x86_64-linux.klocc-gui -L
nix build .#checks.x86_64-linux.klocc-unit-property-tests -L
VM snapshots should stay in the outer loop. They validate package build, artifact generation, compositor startup, input driving, screenshots, and image assertions. That is not supposed to feel like `cargo check`.

Diagnose Rebuilds

Before guessing why Nix rebuilt something, inspect the derivation and build plan.

# What would build or substitute?
nix build .#packages.x86_64-linux.klocc-gui --dry-run

# Get and inspect the derivation.
nix path-info --derivation .#packages.x86_64-linux.klocc-gui
nix derivation show "$(nix path-info --derivation .#packages.x86_64-linux.klocc-gui)"

# Compare two derivations.
nix shell nixpkgs#nix-diff -c nix-diff /nix/store/old.drv /nix/store/new.drv

# Inspect closure size.
nix path-info --recursive --size --closure-size --human-readable .#packages.x86_64-linux.klocc-gui

# Test eval-cache and IFD sensitivity.
nix build .#packages.x86_64-linux.klocc-gui --no-link --option eval-cache false
nix build .#packages.x86_64-linux.klocc-gui --no-link --option allow-import-from-derivation false
